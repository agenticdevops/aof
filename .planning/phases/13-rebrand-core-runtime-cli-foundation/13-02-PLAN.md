    Create `docs/spec/agent-directory-structure.md`. This is the primary specification document for GitAgent-compatible agent definitions.

    The document MUST cover:

    **Directory layout:**
    ```
    agents/my-agent/
    ├── agent.yaml        # Required: minimal manifest (metadata + model only)
    ├── SOUL.md           # Required: identity and system prompt
    ├── RULES.md          # Optional: hard constraints the agent must never violate
    ├── AGENTS.md         # Optional: framework-agnostic fallback prompt
    ├── skills/           # Optional: reusable capability modules
    │   └── skill-name/
    │       ├── SKILL.md  # Skill instructions
    │       └── scripts/  # Optional: helper scripts for this skill
    ├── tools/            # Optional: MCP-compatible tool definitions (YAML schemas)
    ├── workflows/        # Optional: multi-step procedure definitions
    ├── knowledge/        # Optional: reference documents injected into context
    ├── memory/
    │   └── runtime/      # Optional: live state files (dailylog.md, context.md)
    ├── hooks/            # Optional: lifecycle hooks
    │   ├── bootstrap.md  # Instructions run before agent starts
    │   └── teardown.md   # Instructions run after agent completes
    ├── agents/           # Optional: sub-agent definitions (recursive — THIS IS multi-agent)
    ├── examples/         # Optional: few-shot examples for calibration
    └── .gitagent/        # Runtime state (gitignored by OpenAgentiX)
    ```

    **Required files** (agent fails to load without these):
    - `agent.yaml` — minimal manifest (see agent-yaml-v1.md)
    - `SOUL.md` — identity/system prompt markdown. The runtime reads this and uses it as the primary system prompt.

    **How the runtime assembles the system prompt:**
    1. Read `SOUL.md` as the base system prompt
    2. If `RULES.md` exists, append its content after a `## Constraints` header
    3. For each skill in `skills/`: read `SKILL.md` and append after a `## Skill: <name>` header
    4. If `knowledge/` contains markdown files, append their contents as reference material
    5. If `hooks/bootstrap.md` exists, append as pre-run instructions
    The assembled text becomes the `system_prompt` passed to the LLM.

    **tools/ directory:**
    Each file in `tools/` is a YAML schema defining a single tool. Example `tools/kubectl.yaml`:
    ```yaml
    name: kubectl
    description: Run kubectl commands against a Kubernetes cluster
    type: cli
    command: kubectl
    args: ["{{subcommand}}", "{{args}}"]
    ```
    Tool YAML files follow the same schema as `spec.tools` entries from the previous spec. The runtime loads all `.yaml` files in `tools/` and makes them available to the agent.

    **agents/ subdirectory (multi-agent):**
    When an agent directory contains an `agents/` subdirectory, each subdirectory therein is itself an agent definition (same format, recursive). The parent agent can delegate tasks to sub-agents. The runtime loads sub-agents lazily when the parent first delegates to them.

    Example:
    ```
    agents/coordinator/
    ├── agent.yaml
    ├── SOUL.md
    └── agents/
        ├── researcher/
        │   ├── agent.yaml
        │   └── SOUL.md
        └── writer/
            ├── agent.yaml
            └── SOUL.md
    ```

    **skills/ directory:**
    Each subdirectory is a skill module. The `SKILL.md` file contains domain instructions. Skills are composable — an agent can have multiple skills, and each adds to the assembled system prompt.

    Example skill: `skills/postgres-tuning/SKILL.md`:
    ```markdown
    ## PostgreSQL Performance Expert

    When analyzing query performance:
    - Always run EXPLAIN ANALYZE before recommending indexes
    - Consider table statistics (pg_statistic) before suggesting index types
    - Never DROP indexes without understanding impact on write workload
    ```

    **Validation rules:**
    - `agent.yaml` must exist and be parseable
    - `SOUL.md` must exist and be non-empty
    - If `agents/` exists, each subdirectory must itself be a valid agent directory
    - Tool YAML files in `tools/` must match the tool schema
    - Unknown files and directories are ignored (forward compatibility)

    **Compatibility with flat YAML:**
    The OpenAgentiX runtime also loads flat `agent.yaml` files (the v1 format from the previous spec). When `agents_dir` is scanned, both formats are supported:
    - If a path is a directory containing `agent.yaml` → load as GitAgent directory format
    - If a path is a `*.yaml` file with `kind: Agent` → load as flat YAML format (backward compat)

    Include concrete examples for both a minimal agent directory and a full-featured one.

    **Rewrite docs/spec/agent-yaml-v1.md** to document the minimal GitAgent-compatible `agent.yaml` manifest.

    The new agent.yaml is minimal — it carries only metadata and model preference. All behavior is in markdown files.

    ```yaml
    spec_version: "0.1.0"      # Required: OpenAgentiX spec version
    name: my-agent              # Required: unique name (DNS-compatible, lowercase, hyphens)
    version: 0.1.0              # Optional: semver agent version
    description: A helpful assistant  # Optional: human-readable description
    model:
      preferred: anthropic/claude-sonnet-4-6  # Optional: "provider/model" format
    extends: https://github.com/org/base-agent.git  # Optional: inherit from another agent dir
    dependencies:               # Optional: sub-agent dependencies
      - name: fact-checker
        source: https://github.com/org/fact-checker.git
        version: ^1.0.0
        mount: agents/fact-checker
    ```

    Document each field:

    **`spec_version`** (required):
    - Type: string
    - The OpenAgentiX agent directory spec version this agent.yaml conforms to
    - Current value: `"0.1.0"`

    **`name`** (required):
    - Type: string
    - Validation: must match `^[a-z][a-z0-9-]*[a-z0-9]$`, max 63 characters
    - This name is used as the agent's identifier in the gateway and CLI

    **`version`** (optional):
    - Type: string (semver: MAJOR.MINOR.PATCH)
    - Tracks the agent definition version for change management

    **`description`** (optional):
    - Type: string
    - Human-readable description shown in `agentix agents` output

    **`model.preferred`** (optional):
    - Type: string, format: `provider/model`
    - If omitted, falls back to workspace `spec.defaults.model`
    - Supported providers: `anthropic`, `openai`, `google`, `ollama`
    - Examples: `anthropic/claude-sonnet-4-6`, `openai/gpt-4o`, `google/gemini-2.0-flash`

    **`extends`** (optional):
    - Type: string (git URL)
    - Inherit base agent definition from a remote git repository
    - The runtime clones the base agent directory, then overlays the current agent's files

    **`dependencies`** (optional):
    - Type: list of sub-agent dependency specs
    - Each entry: `name` (local alias), `source` (git URL or local path), `version` (semver range), `mount` (where to mount in agents/ subdirectory)
    - Enables importing published sub-agents without bundling them

    **Runtime behavior vs agent.yaml:**
    Note that the following are NOT in agent.yaml (they belong to the runtime or are optional markdown files):
    - System prompt → SOUL.md
    - Constraints → RULES.md
    - Tools → tools/ directory
    - Max iterations, timeout → workspace defaults or runtime defaults
    - Mode (autonomous/semi-autonomous/manual) → workspace defaults
    - Triggers → Phase 15 feature
    - Budget → Phase 17 feature

    Include validation rules, examples (minimal and full), and a reference to agent-directory-structure.md.

    Also note backward compatibility: the old `apiVersion: openagentix.dev/v1 / kind: Agent` flat YAML format is still supported. Document the `AgentManifestFormat` enum (directory vs flat).
