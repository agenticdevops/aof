Create the `subscription/` module directory under `crates/agentix-llm/src/provider/`.

**subscription/mod.rs:**
- Re-exports for the three sub-providers
- Shared helper: function to retrieve bearer token from an `AuthService` (passed via ModelConfig.extra or a shared Arc)

The key architectural insight: subscription providers use the **same API endpoints** as their API-key counterparts but with different auth headers. The approach is to wrap or delegate to the existing provider implementations, replacing the auth mechanism.

**anthropic_sub.rs — AnthropicSubscriptionProvider:**
- Implements `Model` trait
- Uses the exact same Anthropic Messages API endpoint (`https://api.anthropic.com/v1/messages`)
- Instead of `x-api-key: {key}` header, uses `Authorization: Bearer {oauth_token}` header
- Takes a bearer token from config (stored in `ModelConfig.api_key` field — the token IS the credential, just sent as Bearer instead of x-api-key)
- Implementation approach: Construct a reqwest client with Bearer auth header, reuse the same request/response serialization as the existing `anthropic.rs` provider. The simplest approach is to delegate to the existing provider logic with a modified headers map.
- On 401: return error with message indicating token may have expired (agent run fails per CONTEXT.md — no auto-fallback)

**openai_sub.rs — OpenAISubscriptionProvider:**
- Implements `Model` trait
- Uses the official OpenAI API endpoint (`https://api.openai.com/v1/chat/completions`) — same as API key mode per CONTEXT.md (NOT the unofficial chatgpt.com backend-api)
- Auth: `Authorization: Bearer {oauth_access_token}` — identical header format to API key mode, but the token is an OAuth token from auth.openai.com instead of an sk- API key
- Implementation: This is essentially the same as the existing OpenAI provider. The simplest approach is to just use the existing `OpenAIProvider::create()` with the OAuth token in `ModelConfig.api_key` since OpenAI API already uses Bearer auth. If the existing provider works with OAuth tokens directly, this adapter can be a thin wrapper or even just factory routing.

**google_sub.rs — GoogleSubscriptionProvider:**
- Implements `Model` trait
- Uses Google's Generative Language API: `https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`
- Auth: `Authorization: Bearer {oauth_access_token}` instead of API key in URL params
- The existing `google.rs` provider likely uses `?key=API_KEY` auth. The subscription version swaps this for a Bearer header.
- Reuse request/response serialization from existing `google.rs`
- Streaming: `?alt=sse` parameter

For all three adapters, the `create()` method should accept a `ModelConfig` where `api_key` contains the OAuth access token. The subscription routing happens at the factory level; the adapters just ensure the right auth mechanism is used.

**Important:** These adapters do NOT handle token refresh themselves. Token refresh is handled by the AuthService (plan 02) at a higher level — before creating the model, the caller ensures the token is valid. If it expires mid-run, the HTTP 401 propagates as an error.
